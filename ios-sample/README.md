# openliveness iOS sample

Dev harness that exercises the openliveness iOS SDK end-to-end on a real
device. **Not shippable** — the red "DEV HARNESS" banner is permanent so
a screenshot of a running build cannot be mistaken for a production
integration, and the server-side `stub_mode` allow-list is the second
half of the gate against a hostile fork that strips the banner.

The equivalent Android dev harness lives in `../android-sample`; this
README documents the iOS-specific build + CI path. Everything else
(design, scope, phase roadmap) lives in the top-level README.

## Local build

The Xcode project is **not** checked in — `project.yml` is the single
source of truth, and `OpenLivenessSample.xcodeproj` is generated by
XcodeGen on every build. Rationale is in the comment at the top of
`project.yml`.

```bash
brew install xcodegen
cd ios-sample
xcodegen generate
open OpenLivenessSample.xcodeproj
```

Simulator builds work out of the box — the Debug configuration enables
the `OPENLIVENESS_STUB_ALLOWED` compile flag so `CDLSession.start()` can
run its stub-liveness path without a real `LandmarkStream`. App Attest
is unavailable on the Simulator (`DCAppAttestService.isSupported` is
false there), so the relay sees `hw_attestation_status: unsupported`
rather than `.ok` — which is correct, not a bug.

To exercise App Attest, you need a signed build on a real device. The
two paths are:

1. **Local**: flip `CODE_SIGN_STYLE: Manual` + set `DEVELOPMENT_TEAM`
   in `project.yml` (don't commit the change), regenerate, run on a
   tethered iPhone.
2. **CI → TestFlight**: push a `v*` tag OR run the `iOS Sample`
   workflow manually with `upload_to_testflight=true`. See below.

## TestFlight distribution

`.github/workflows/ios-sample.yml` has two jobs:

- **`pr-build`** runs on every PR + branch push. Simulator build only,
  no signing, no secrets. Forks without an Apple Developer account
  still get green CI from this job.
- **`testflight`** runs on `v*` tag pushes and manual dispatch. Builds
  a signed archive and uploads the .ipa to TestFlight.

The TestFlight job is secret-gated: the `if:` guard skips it entirely
when the required secrets aren't set, so a fork can't accidentally
trigger a broken signing attempt.

### Required repository secrets

Add these under **Settings → Secrets and variables → Actions → New
repository secret**. Then (optional but recommended) scope them to the
`testflight` environment so you get a manual approval gate before any
upload.

| Secret                              | How to obtain                                                                                                                                                                 |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `APP_STORE_CONNECT_API_KEY_ID`      | App Store Connect → **Users and Access → Integrations → App Store Connect API** → create a key with **App Manager** role. The ID is the short alphanumeric shown next to the key name. |
| `APP_STORE_CONNECT_ISSUER_ID`       | Same page, header area. One per tenant.                                                                                                                                       |
| `APP_STORE_CONNECT_API_KEY_BASE64`  | Download the `.p8` once at key creation time (you cannot re-download it later). Run `base64 -i AuthKey_XXXXXXX.p8 \| pbcopy` and paste the result.                            |
| `APP_STORE_CONNECT_TEAM_ID`         | App Store Connect → **Membership → Team ID**. 10 characters.                                                                                                                 |

The private key is base64-encoded because GitHub secrets round-trip
multiline strings poorly — the workflow decodes it back into
`~/.appstoreconnect/private_keys/` at runtime, matching the standard
location `xcodebuild` / `altool` look in.

### Triggering a release

```bash
git tag v0.1
git push origin v0.1
```

...or go to **Actions → iOS Sample → Run workflow**, select the branch,
and set **Upload a signed build to TestFlight** to `true`. The upload
appears in TestFlight under **TestFlight → iOS → Builds** a few minutes
after `altool` reports success; expect another 10–20 min for Apple to
finish processing before internal testers can install.

### Internal testers

Add your Apple ID under **TestFlight → Internal Testing** in App Store
Connect. Internal testers skip Apple's review queue, which is the whole
reason this path is the recommended way to iterate on a dev harness
without owning a modern Mac — tag, wait ~15 min, install from
TestFlight on the device.

## Bundle identifier + entitlements

`project.yml` sets `PRODUCT_BUNDLE_IDENTIFIER=dev.openliveness.sample`.
If a fork wants to ship their own TestFlight copy, change that value
AND create a matching App ID in App Store Connect with App Attest
enabled — otherwise `DCAppAttestService.generateKey()` throws
`invalidKey` on first run.

`Resources/Sample.entitlements` requests the App Attest capability in
`development` mode. **The entitlement value is used verbatim at runtime**
— `ExportOptions.plist` and the signing pipeline do NOT rewrite it. That
means both local-device and TestFlight builds talk to Apple's development
attestation endpoints, which is deliberate for a dev harness (laxer
freshness checks, no production assertion-quota pressure). To exercise
the production App Attest endpoints, change the entitlement to
`production` — nothing else in the build pipeline needs to change.
